# Tech stack

Status: proposed (confirm before building on it)
Date: 2026-11-25

## Decision
- **Backend**: Python 3.12, FastAPI, SQLAlchemy + Alembic. Python because PDF parsing,
  NLI models and LLM SDKs all live there.
- **Storage**: PostgreSQL + pgvector. Thousands of PDFs → likely 10^5–10^6 statements;
  one database holds relational data, embeddings and the link graph (edges table).
- **Jobs**: background worker with a Postgres-backed queue (e.g. procrastinate), so
  ingest/extraction of thousands of PDFs is resumable and needs no extra Redis.
- **PDF parsing**: pluggable too; start with Docling or GROBID (sections, references,
  page coordinates), PyMuPDF as a fast fallback.
- **Frontend**: React + TypeScript (Vite), talking to the FastAPI JSON API.
- **Dev setup**: docker compose (postgres, api, worker, web); uv for Python deps.

## Alternatives
- SQLite + FAISS: simpler, but weak for concurrent workers and this scale.
- Neo4j for the fact graph: nicer graph queries, but a second database to sync;
  revisit if graph queries outgrow SQL.
- HTMX/server-rendered UI: less code, but the graph view and review screens need
  rich client interaction.
